# Trusted Grounding Layer

Grounding is the process of ensuring that an agent's actions and outputs are anchored in verified facts and governed by host-defined policies. In `dart_monty`, grounding is achieved through a strict architectural "Air Gap" that separates untrusted Python code from the host infrastructure.

## The Separation of Concerns

To build a secure and reliable agent runtime, `dart_monty` distinguishes between two distinct worlds:

1. **The Guest (Untrusted)**: Python code generated by an LLM. This code is treated as suspicious and is confined to a zero-privilege sandbox with hard resource limits.
2. **The Host (Trusted)**: The Dart/Flutter application and the `MontyBridge`. This layer manages state, persistence, routing, and policy enforcement.

The bridge acts as the single, controlled chokepoint where these two worlds interact.

## Call Attribution via `CallRole`

Every interaction with the host is attributed to a `CallRole`. This allows the bridge to distinguish between actions requested by the LLM and maintenance tasks performed by the infrastructure.

| Role | Source | Enforcement | Use Case |
|------|--------|-------------|----------|
| **`InfraCall`** | Internal Harness | Bypassed | State restoration, function listing, heartbeat |
| **`ToolCall`** | Python Script | Full Policy | Search, database query, file write |

### Role Integrity

A common attack vector in agentic systems is **Role Escalation**, where untrusted code attempts to trigger infrastructure functions to bypass security. `dart_monty` prevents this by making the host-side declaration authoritative:

```dart
HostFunction(
  schema: const HostFunctionSchema(name: 'secure_search', ...),
  handler: (args) async => ...,
  // Authoritative: Python cannot override this to InfraCall
  role: const ToolCall(), 
)
```

## Middleware as Validation Gates

The grounding layer uses an "Onion" middleware model to wrap tool execution in multiple layers of validation.

1. **Input Grounding**: Sanitizing arguments (e.g., stripping SQL injection patterns or PII) before they reach the tool handler.
2. **Output Grounding**: Asserting invariants on the data returned to the LLM. If a tool returns malformed data or sensitive information, the middleware can redact it or throw an error before the LLM sees it.

See the [Middleware Tutorial](../tutorials/bridge-middleware.md) for implementation patterns.

## System Prompt Integrity

Grounding also applies to the LLM's understanding of its environment. The `PluginRegistry` automatically generates a system prompt based on the registered tool schemas.

- **Infrastructure Hidden**: Internal functions like `__restore_state__` are omitted from the generated prompt.
- **Context Injection**: Use `systemPromptPrefix` to provide "Grounding Instructions" (e.g., "You only have access to the following tools...") that the guest code cannot modify or see.

## Virtualized OS Surface

The `OsProvider` provides the final layer of grounding by virtualizing the operating system surface.

- **Path Mapping**: Python scripts think they are writing to `/data/log.txt`, but the host maps this to an isolated `MemoryFsProvider` or a specific subdirectory on disk.
- **Deterministic Environment**: By providing a controlled `TimeOsProvider`, you ensure the agent cannot use system time as a side-channel or for non-deterministic logic unless explicitly allowed.
